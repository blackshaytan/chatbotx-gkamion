# Staff Chat — Stage 1 (схема и сервисы) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** в ядре внутренней переписки появляются личные чаты (`direct` — два сотрудника, `agent` — канал «API-клиент → сотрудник»), а `chatService` умеет открывать, перечислять, читать, писать, править, удалять, отмечать прочитанным и считать непрочитанное. Публичного API, интерфейса и realtime ещё нет — этап закладывает схему и сервисы, на которых стоят этапы 2–4 и 6.

**Architecture:** миграция `staff_chat` (значения enum, три колонки `InternalThread`, два индекса, частичный уникальный индекс `Notification`) → `chatRepository` (`packages/database/src/repositories/chat/`, только сырые запросы; get-or-create — `INSERT … ON CONFLICT DO NOTHING` + повторное чтение) → `chatService` (`packages/business/src/chat/`: проверки, транзакции, права) поверх уже существующего `internalThreadService` (сообщения-комментарии, правка/удаление, `canEditComment`/`canDeleteComment` с `isOwner = false`). Вложения обобщаются до `threadAttachmentPrefix` (`tasks` | `chats`). `deleteMembersForUser` ограничивается лентами `type = 'task'`.

**Tech Stack:** Drizzle (beta.22) + drizzle-kit, PostgreSQL, vitest (моки репозиториев, рендер SQL через `PgDialect`, опциональные `test:db`).

**Spec:** `docs/superpowers/specs/2026-10-27-staff-chat-design.md` (разделы 3, 4.1–4.3, 4.7, 8, 9; этап 1 из раздела 10; решения D1, D2, D5, D8; ключ `agent:<userId>:staff` — 13.3). Факты по коду: `.superpowers/sdd/chat-explore.md`. Предыдущий этап того же ядра: `docs/superpowers/plans/2026-10-23-team-tasks-stage-4.md`.

## Deviations from the spec (decided while planning)

1. **Стадия уведомлений.** В этап 1 входят только **типы** `Notification` (`chatMessage`, `entityType: "chat"`, `ChatNotificationPayload`) и частичный уникальный индекс. `notifyChatMessage`, `markReadForEntity`, ключ `chatMessage` в `workspaceMemberNotificationTypesSchema`, прочтение уведомления внутри `markRead`, URL чата в колокольчике — этап 4 (раздел 10). Пока чатовых уведомлений нет, `notificationService.listForUser` явно фильтрует `entityType = 'task'` (чтобы расширение типов колонки не сломало вывод `notificationsAPI` и тип `taskNotificationTypes` в `notification-item`); этап 4 снимает фильтр вместе с `countUnread`.
2. **Get-or-create — в репозитории** (`chatRepository.getOrCreate`: insert on conflict + участники + повторное чтение), сервис добавляет проверки и транзакцию. Так гарантию «параллельные вызовы → один чат» можно проверить на настоящем PostgreSQL в `packages/database/__tests__/integration/` (сервис из этого пакета недоступен), а юнит-тесты сервиса — на in-memory подмене с теми же семантикой `ON CONFLICT`.
3. **Время считает БД.** `lastMessageAt` обновляется `GREATEST(coalesce(lastMessageAt,'-infinity'), (SELECT createdAt FROM InternalMessage WHERE id = :messageId))`, `markRead(upToMessageId)` — подзапросом по `createdAt` сообщения, курсор страницы сообщений — подзапросом `(createdAt, id) < (SELECT …)`. JS `Date` режет микросекунды PostgreSQL до миллисекунд, и сравнение «на стороне приложения» ошибалось бы на сообщениях одной миллисекунды. Формулы спеки (4.2) сохранены.
3a. **Отметка прочитанного без `upToMessageId`** берёт `now()` БД, как в спеке; сообщение из транзакции, начатой раньше отметки и закоммиченной позже, может оказаться «прочитанным» — риск тот же, что у лент задач, фронт передаёт `upToMessageId` (этап 3).
4. **`ChatActor` / `ChatScope`.** Сервис принимает `ChatActor = { kind: "user"; userId } | { kind: "api"; label }` и выводит доступ из актора (сотрудник — только чаты, где он участник; токен — любой чат пространства, D6); `scope` для `list`/`get`/`listMessages` передаётся явно (`{ kind: "member"; userId }` | `{ kind: "workspace" }`) — приложение решает, кому разрешён `workspace` (сессия поддержки, токен, этапы 2–3). Для `internalThreadService` актор приводится к `TaskActor` с `isOwner: false` (D5).
5. **Распознавание упоминаний отключается параметром** `parseMentions?: boolean` (по умолчанию `true`) у `internalThreadService.postComment` / `editComment` — поведение лент задач не меняется; чат передаёт `false` и пишет пустые `mentions` без обращений к `taskRepository`.
6. **Лимиты.** `CHAT_LIMITS` (рядом с `TASK_LIMITS`, `partials/task.ts`) содержит длину сообщения и размеры страниц; лимиты вложений (10 × 25 МБ) остаются одной константой `THREAD_ATTACHMENT_LIMITS` в `attachments.ts` (`TASK_ATTACHMENT_LIMITS` — алиас для существующего теста).
7. **Ключ ассистента (`agent:<userId>:staff`) закладывается чистой функцией** `buildAgentChatKey` и параметром `channel` метода `open` уже сейчас — это единственное место построения ключа (13.3); обёртка `openAgentChannel`, `ExternalAgent.apiTokenId` и привязка токена — этап 6.
8. **Результат `send`/`edit`/`delete`** содержит `memberUserIds` и `recipientUserIds` (участники без автора) — вход для уведомления и realtime этапов 3–4; сам сервис этапа 1 их не рассылает.
9. **Вне этапа 1** (не добавлять): scope `chats`, `requireTokenScope`, `features/chats/*`, маршрут `/media/chat-attachment` и вид токена `chatAttachment`, `isSupportSession` в контексте, `RealtimeTopic.staffChats`, `workspaceMemberNotificationTypesSchema.chatMessage`, колонки/таблицы этапа 6 (`ExternalAgent.purpose`, `apiTokenId`, `ExternalAgentChatState`, `InternalMessage.dedupeKey`), `docs/staff-chat.md`.

## Открытые вопросы (не блокируют этап 1)

1. **`taskService.findAttachment`** (`task/service.ts:648-680`) ищет сообщение по `workspaceId` + id, не проверяя тип треда. Подписанный токен `taskAttachment` выдаётся только для сообщений задач, поэтому эксплуатации нет, но после появления чатов стоит ограничить поиск лентами `type = 'task'` (один `join` в `internalThreadRepository.findMessage`-варианте) — предлагается отдельным мелким коммитом перед этапом 2.
2. **Текст 403 для чатов.** `internalThreadService.editComment/deleteComment` бросают `taskForbiddenException` («You are not allowed to change this task», код `FORBIDDEN`). Для чата формулировка неточная; код и статус те, что нужны. Спека 8 допускает «общий forbidden». Если нужно — `chatForbiddenException` в `chat/` и подмена в `chatService` отдельным шагом.
3. **Этап 4, уточнение к 4.4 спеки:** колонки времени — `timestamptz`, поэтому условие прочтения `(payload->>'lastMessageAt')::timestamp <= :upTo` следует писать с `::timestamptz` (ISO-строка с `Z`, `ChatNotificationPayload.lastMessageAt`), иначе результат зависит от часового пояса сессии.
