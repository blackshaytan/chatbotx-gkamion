# Внешний ИИ-агент (Hermes) отвечает клиентам ChatbotX — дизайн

Дата: 2026-10-21
Ветка: `feature/ru-channels-max-zzap-drom`
Статус: согласовано, ожидает ревью спеки

## 1. Цель и контекст

На VPS уже работает Hermes Agent (Nous Research, `/opt/hermes-build/hermes-agent`, данные в `/opt/hermes-data`). Профиль `assistant` общается с клиентами gKamion: инструкции в `SOUL.md`, память, база знаний Геки, MCP `gkamion` в клиентском режиме. Сейчас он работает только в Telegram напрямую.

Нужно, чтобы этот же профиль отвечал клиентам в диалогах ChatbotX (MAX, ZZAP, DROM и другие каналы). Hermes остаётся «мозгом» со своими инструкциями и данными; ChatbotX — каналы, входящие, операторы и контроль.

Решения, согласованные с пользователем:

- Hermes отвечает на **каждое** сообщение клиента, пока у диалога включён бот. Сценарии для этого не нужны.
- В диалог переходит человек, если Hermes сам передал его (не знает ответа, клиент просит менеджера) или менеджер написал в диалог. Вернуть диалог Hermes — кнопкой «Вернуть боту». Автовозврат — настройка «через N часов / никогда», по умолчанию «никогда».
- Используется существующий профиль `assistant`, новый профиль не создаётся. Остальные профили Hermes не меняются.
- Telegram-бот, через который клиенты сейчас пишут `assistant`, остаётся подключённым к Hermes напрямую. В ChatbotX этот бот не подключается (один бот не может отдавать сообщения в два места). Перенос — отдельным шагом позже.
- Способ подключения — встроенная интеграция «Внешний ИИ-агент» в ChatbotX (не готовые ИИ-агенты ChatbotX и не вебхук + MCP).

**Не входит:** «Джарвис» для сотрудников (следующий этап), расшифровка голосовых (Hermes получает ссылку на файл), отключение Геки, перенос Telegram-бота `assistant` в ChatbotX.

## 2. Что уже есть и что переиспользуем

- `Conversation.botEnabled` и `botResumeAt` (`packages/database/src/schema/conversation.ts`). `conversationService.disableBotState` / `enableBotState` выключают и включают бота и шлют события «передан человеку / боту». Сообщение менеджера из ChatbotX выключает бота (`disableBotAction` в `message-input.tsx`), сейчас с автовозвратом через `BOT_DISABLE_DURATION_MS` (24 часа).
- Публичный API `conversations` уже умеет переключать бота (`botEnabled: true/false`) — значит, это доступно Hermes через MCP-сервер ChatbotX.
- Приём сообщений — `receiveMessage` в `apps/worker/src/integration/handlers/received-message.ts`, с флагом `canAutomate` (активное пространство, нет подавления автоматизации).
- Отправка — обычный путь исходящего сообщения ChatbotX (`ChatJobAction.sendMessage`), тот же, что у сценариев.
- Шифрование секретов — `@chatbotx.io/encryption`. Журнал ошибок третьих сторон — событие `error-log:recorded`.
- Hermes `api_server` (`gateway/platforms/api_server*.py`), ключ `API_SERVER_KEY` / `extra.key`:
  - `POST /v1/runs` — фоновый запуск хода, сразу возвращает `run_id`; заголовок `X-Hermes-Session-Key` — постоянная память сессии на ключ, `Idempotency-Key` — повтор запроса не запускает ход второй раз;
  - `GET /v1/runs/{run_id}/events` — поток событий (SSE) с повтором с места обрыва (`Last-Event-ID`): `tool.started`, `tool.completed`, `message.interim` (промежуточная реплика агента между вызовами инструментов), `message.delta`, `run.completed` (итоговый ответ), `run.failed`, `run.interrupted`;
  - `GET /v1/runs/{run_id}` — статус и итог (`output`) для проверки после перезапуска worker;
  - `POST /v1/runs/{run_id}/steer` — добавить текст в работающий ход (409, если ход уже не принимает);
  - `POST /v1/runs/{run_id}/stop` — остановить ход.

## 3. Модель данных

**`ExternalAgent`** — одна запись на рабочее пространство:

- `id`, `workspaceId` (уникально), `provider`: `hermes`
- `baseUrl` (например `http://127.0.0.1:8647/v1`), `apiKey` — зашифрован
- `enabled` (общий выключатель), `resumeAfterHours` (целое или пусто = «никогда»)
- `maxRunMinutes` (общий лимит хода, по умолчанию 30), `progressMessage` (сервисное сообщение-страховка, по умолчанию «Работаю над вашим запросом, это займёт несколько минут»; пусто — не отправлять)
- `lastCheckedAt`, `lastCheckStatus` (`ok` / `error`), `lastCheckError`
- `createdAt`, `updatedAt`

**`ExternalAgentInbox`** — в каких каналах агент отвечает: `externalAgentId`, `inboxId` (уникальная пара). По умолчанию записей нет — агент нигде не отвечает, пока пользователь не включит каналы.

**`ExternalAgentConversationState`** — курсор по диалогу:

- `conversationId` (PK), `workspaceId`
- `lastHandledMessageId` — последнее сообщение клиента, уже отправленное Hermes
- `runId`, `runStartedAt`, `lastEventAt`, `lastEventSeq` — текущий ход (пусто, если хода нет)
- `lastProgressSentAt`, `lastProgressText`, `progressFallbackSentAt` — промежуточные сообщения текущего хода
- `failureCount`, `lastError`, `updatedAt`

Таблицы — через drizzle-миграцию; миграцию генерирую и показываю, применяю только после явного разрешения.

## 4. Как идёт сообщение

1. `receiveMessage` сохранило входящее сообщение клиента (`messageType = incoming`), `canAutomate = true`.
2. Проверка (одним запросом через сервис): у пространства есть `ExternalAgent` с `enabled = true`, inbox диалога есть в `ExternalAgentInbox`, у диалога `botEnabled = true`. Иначе — ничего не делаем.
3. В очередь `chat` ставится отложенная задача `externalAgentReply` с `jobId = externalAgentReply:<conversationId>` и задержкой 5 секунд. Если такая задача уже ждёт, новая не создаётся — она заберёт и новое сообщение (склейка сообщений подряд).
4. Задача `externalAgentReply` (под `withBlockedOwnerGuard`):
   1. Берёт блокировку диалога в Redis (чтобы два worker не вели диалог одновременно).
   2. Перечитывает настройки и `botEnabled` — если бот выключен или канал убран, выходит.
   3. Выбирает сообщения клиента после `lastHandledMessageId`. Пусто — выходит.
   4. Если у диалога уже идёт ход (`runId` задан): отправляет новые сообщения в него через `steer` и сдвигает курсор. Ответ 409 — ход уже заканчивается, сообщения останутся для следующего хода. Выходит.
   5. Иначе собирает ход: тексты по порядку; для фото и файлов — подписанные ссылки (срок 24 часа) с типом; служебный контекст отдельной частью: имя клиента, канал, `conversationId`, `contactId`, `workspaceId`.
   6. `POST {baseUrl}/runs` с заголовками `Authorization: Bearer <apiKey>`, `X-Hermes-Session-Key: chatbotx:<workspaceId>:<conversationId>`, `Idempotency-Key: <conversationId>:<последний messageId хода>`. Сохраняет `runId`, `runStartedAt`, сдвигает курсор.
   7. Ставит задачу `externalAgentWatch` для этого диалога.
5. Задача `externalAgentWatch` (одна на диалог, `jobId = externalAgentWatch:<conversationId>`) читает поток событий хода с `Last-Event-ID = lastEventSeq` и обновляет `lastEventAt` / `lastEventSeq` на каждое событие:
   - `message.interim` — промежуточная реплика Hermes («Принял список из 12 позиций, проверяю наличие и цены»). Если бот включён, текст не пустой, не совпадает с `lastProgressText` и с `lastProgressSentAt` прошло не меньше 30 секунд — отправляется клиенту сообщением бота. Иначе отбрасывается.
   - `tool.started`, `tool.completed`, `message.delta` — клиенту не отправляются, только продлевают «жизнь» хода.
   - `run.completed` — перепроверка `botEnabled`; непустой итоговый текст уходит клиенту; ход закрывается (`runId` = пусто), `failureCount` = 0. Если за время хода пришли сообщения клиента, которые не попали в `steer`, — ставится новая `externalAgentReply`.
   - `run.failed`, `run.interrupted` — как ошибка хода (раздел 6).
   - **Страховка:** если с `runStartedAt` прошло 90 секунд, а клиенту ещё ничего не ушло (ни промежуточных, ни итога), один раз отправляется `progressMessage` (`progressFallbackSentAt`).
   - **Лимиты:** нет ни одного события 5 минут — ход завис; с `runStartedAt` прошло больше `maxRunMinutes` — превышен общий лимит. В обоих случаях — `stop` и обработка ошибки (раздел 6).
   - Обрыв потока или перезапуск worker: задача повторяется, сначала читает `GET /v1/runs/{runId}` (ход мог закончиться, итог — в `output`), затем переподключается к потоку с `lastEventSeq`. Итог и промежуточные сообщения не отправляются дважды: отправка идёт только по событиям с номером больше `lastEventSeq`.

Текст клиента передаётся Hermes как сообщение пользователя (`input`), служебный контекст — отдельной частью с пометкой, что это данные ChatbotX, а не инструкции.

## 5. Передача человеку и возврат

- **Hermes передаёт сам:** вызывает через MCP ChatbotX `conversations.update` с `botEnabled: false` и короткой причиной. Причина пишется во «Входящие» системной заметкой (через существующие заметки диалога). Описание инструмента подсказывает Hermes, откуда брать `conversationId` (из служебного контекста хода).
- **Менеджер написал сам:** как сейчас — бот выключается.
- **Если в момент выключения бота идёт ход** (`runId` задан): ChatbotX вызывает `stop`, ни промежуточные, ни итоговый ответы этого хода клиенту не отправляются.
- **Автовозврат:** когда бот выключается в диалоге канала, где включён внешний агент, `botResumeAt` берётся из `ExternalAgent.resumeAfterHours`: пусто — `botResumeAt = null` (только кнопкой), число — `now + N часов`. Для остальных каналов поведение не меняется (24 часа). Расчёт — в одном месте, в `conversationService.updateBotEnabled`, через новый метод сервиса внешнего агента.
- **Возврат кнопкой «Вернуть боту»:** существующий `enableBotState`. Сообщения, пришедшие, пока диалог был у человека, Hermes **не** получает задним числом: при возврате курсор сдвигается на последнее сообщение диалога. Историю Hermes видит в своей сессии только из своих ходов, поэтому в первом ходе после возврата служебный контекст добавляет последние 10 сообщений диалога (клиент и менеджер) как справку.

## 6. Ошибки

| Ситуация | Поведение |
|---|---|
| Долгий ход (проценка, подбор по VIN), события идут | не ошибка, сколько бы ни длился, в пределах `maxRunMinutes` |
| `POST /runs` не прошёл: 5xx или сеть недоступна | повтор задачи BullMQ, до 3 попыток с паузой 30 с / 2 мин / 5 мин; `Idempotency-Key` не даёт Hermes запустить ход дважды |
| Поток событий оборвался | переподключение с `lastEventSeq`; если Hermes недоступен — те же повторы |
| Нет событий 5 минут (завис) или превышен `maxRunMinutes` | `stop`; клиенту — «Передал ваш запрос менеджеру»; диалог передаётся человеку с заметкой «ИИ-агент не завершил ответ»; событие `error-log:recorded` |
| `run.failed` / `run.interrupted`, или все повторы не удались | `failureCount++`, `lastError`; клиенту — «Передал ваш запрос менеджеру»; диалог передаётся человеку (`disableBotState`) с заметкой «ИИ-агент недоступен»; событие `error-log:recorded`; технических подробностей клиент не получает |
| 401/403 от Hermes | без повторов: передача человеку, ошибка в журнал, `lastCheckStatus = error` |
| Клиент пишет, пока Hermes думает | второй параллельный ход не запускается (блокировка + `jobId`); новые сообщения уходят в работающий ход через `steer`, а если он уже не принимает — следующим ходом |
| Канал доставил то же сообщение повторно | сообщение уже сохранено один раз (существующая дедупликация), курсор не даёт ответить дважды |
| Пустой ответ Hermes | не отправляется, курсор сдвигается |
| Ошибка отправки в канал | существующая обработка ошибок отправки ChatbotX |
| Владелец заблокирован, пробный период истёк | `withBlockedOwnerGuard` / `canAutomate` — агент молчит |
| Внешний агент выключен или канал убран из списка, пока задача ждала | задача перепроверяет настройки и выходит |

## 7. Настройки и интерфейс

- **Настройки → Внешний ИИ-агент** (только владелец и `superAdmin`):
  - адрес, ключ (поле «задан / не задан», ключ никогда не показывается);
  - общий выключатель;
  - список каналов (inbox) с переключателями; по умолчанию все выключены;
  - «Возвращать диалог агенту»: «никогда» / «через N часов»;
  - «Общий лимит ответа, минут» (по умолчанию 30) и «Сервисное сообщение, если агент долго молчит» (по умолчанию «Работаю над вашим запросом, это займёт несколько минут»; можно очистить, чтобы не отправлять);
  - кнопка «Проверить подключение» — короткий запрос к Hermes (`GET {baseUrl}/models` или пробный ход в отдельной сессии `chatbotx:healthcheck`), результат и время последней проверки.
- **Диалог во «Входящих»:** существующий значок «бот / человек» и кнопка «Вернуть боту»; заметки «Передано человеку: <причина>» и «ИИ-агент недоступен».
- Все строки — через `useTranslations()`, ключи в 22 локалях (русский перевод, в остальных — английский).

## 8. Публичный API, CLI, MCP

В `features/external-agent/api/public.ts`, за `workspaceTokenAuthAPIForScope("externalAgent")`, вложено в `routers/public.ts`:

- `externalAgent.get` — настройки без ключа (`hasApiKey: boolean`), список `inboxIds`, последняя проверка.
- `externalAgent.update` — адрес, ключ (запись без чтения), `enabled`, `inboxIds` (id из `inboxes.list`), `resumeAfterHours`, `maxRunMinutes`, `progressMessage`.
- `externalAgent.test` — проверка подключения, возвращает `{ ok, status, error, checkedAt }`.

UI и API вызывают один сервис `externalAgentService` (`packages/business`). После — навык `cli-mcp-docs`.

## 9. Сторона Hermes (выполняется отдельно, с разрешения пользователя)

В профиле `assistant` (`/opt/hermes-data/profiles/assistant/config.yaml`):

- `platforms.api_server`: `enabled: true`, `extra.host: 127.0.0.1`, свободный порт (например 8647), `extra.key` — новый ключ (хранится в секретах Hermes и в `.secrets/` ChatbotX, не печатается).
- `platform_toolsets.api_server`: `gkamion`, `memory`, `chatbotx` — без `terminal`.
- `mcp_servers.chatbotx`: MCP-сервер ChatbotX с отдельным токеном рабочего пространства. Права токена — только диалоги, сообщения, заметки, контакты, теги; без токенов API и настроек.
- В `SOUL.md` (или навык профиля) — правила для ходов из ChatbotX:
  - отвечать клиенту текстом;
  - если работа займёт больше ~30 секунд (список деталей, подбор по VIN), сначала коротко написать, что делаешь и сколько примерно ждать; на долгой задаче изредка сообщать о ходе работы («Проверил 8 из 12 позиций»). Эти реплики ChatbotX отправляет клиенту как промежуточные сообщения;
  - если нужен менеджер — вызвать передачу человеку с причиной и коротко сообщить клиенту, что менеджер подключится.

Чтобы настройки применились, службу профиля надо перезапустить (около минуты без ответов в Telegram). Перезапуск — только после «можно» от пользователя. Worker ChatbotX в `docker-compose.prod.yml` работает с `network_mode: host`, поэтому `http://127.0.0.1:<порт>/v1` ему доступен, и `api_server` слушает только `127.0.0.1`.

## 10. Безопасность

- Ключ Hermes — зашифрован в БД, наружу не отдаётся ни в UI, ни в API.
- Порт `api_server` слушает только `127.0.0.1`; проверка `ss -ltnp` после перезапуска.
- Токен MCP ChatbotX для Hermes — отдельный, на одно пространство, с минимальным набором прав; не может создавать токены (инвариант 23).
- Текст клиента не попадает в инструкции; служебный контекст помечен как данные.
- Подписанные ссылки на файлы — с ограниченным сроком, ключи в рамках `workspaceId`.
- Логи — через структурный логгер, ошибки с ключом `err`, без текста ключа и без полных текстов сообщений.

## 11. Тестирование

Без настоящего Hermes (HTTP подменяется в тестах):

- `externalAgentService`: проверка «должен ли отвечать» (выключено, нет канала, бот выключен, пространство неактивно); `resumeAfterHours` → `botResumeAt` (никогда, N часов; другие каналы — 24 часа).
- Задача `externalAgentReply`: склейка нескольких сообщений; повторная задача не создаёт второй ход; сообщение во время хода уходит через `steer`, при 409 — следующим ходом; бот выключен до запроса — ничего не отправлено; курсор после успеха и после выключения; ход после возврата с последними 10 сообщениями.
- Задача `externalAgentWatch` (поток событий подменяется): `message.interim` отправляется, повтор текста и чаще 30 секунд — нет; `tool.*` клиенту не уходят; итог после выключения бота не отправляется, вызывается `stop`; страховка `progressMessage` ровно один раз после 90 секунд тишины перед клиентом и не отправляется, если Hermes уже написал; зависание 5 минут и `maxRunMinutes` → `stop` и передача человеку; перезапуск посреди хода — итог из `GET /runs/{id}` без повторной отправки уже отправленного.
- Ошибки: повторы `POST /runs`, `Idempotency-Key` одинаковый для повторов, передача человеку после последней попытки с сообщением клиенту, 401 без повторов.
- Публичный API: `get` не возвращает ключ, `update` принимает только inbox своего пространства, `test` отдаёт машинно-читаемый результат.
- Тесты и проверка типов — только на GitHub (`gkamion-checks.yml`), не на VPS.
- Ручная проверка: пользователь сам включает агента в одном тестовом канале и пишет туда.

## 12. Этапы реализации

1. Таблицы и миграция (показать SQL, применить после разрешения).
2. `externalAgentService` + публичный API + тесты.
3. Задачи `externalAgentReply` и `externalAgentWatch` в worker, постановка из `receiveMessage`, `stop` при передаче человеку, автовозврат в `updateBotEnabled`.
4. Интерфейс настроек и заметки в диалоге, i18n.
5. CLI/MCP документация (`cli-mcp-docs`).
6. Сторона Hermes: конфиг профиля `assistant`, токен MCP, перезапуск — после разрешения.
7. Сборка, деплой, ручная проверка на тестовом канале.
