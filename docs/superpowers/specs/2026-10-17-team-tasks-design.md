# Задачи между сотрудниками ChatbotX — дизайн

Дата: 2026-10-17
Ветка: `feature/ru-channels-max-zzap-drom` (реализация — после спеки `2026-10-17-ru-channels-max-zzap-drom-design.md`)
Статус: согласовано, ожидает ревью спеки

## 1. Цель и контекст

Дать сотрудникам рабочего пространства ChatbotX возможность ставить друг другу задачи, обсуждать их и получать уведомления. ИИ-агент Hermes и сценарии бота тоже должны уметь ставить задачи людям (например: «проверить наличие запчасти на складе и ответить клиенту до 15:00»).

Принцип, подтверждённый исследованием (Chatwoot, Twenty, EspoCRM, Bitrix24, обсуждения на Reddit): **чат — для скорости, задачи — для ответственности**. Поэтому сначала задачи с лентой обсуждения внутри каждой задачи (подход Bitrix24: «чат задачи»), а отдельный чат сотрудников — следующим подпроектом на том же ядре внутренней переписки.

**Входит:**
- задачи: ответственный (сотрудник или команда), наблюдатели, срок, напоминание, статус, приоритет, связь с контактом, диалогом и сообщением;
- лента задачи: комментарии с @упоминаниями сотрудников и команд, вложения, системные события;
- создание задачи из сообщения клиента одним кликом;
- шаг сценария «Создать задачу»;
- уведомления: центр уведомлений в интерфейсе, push в браузере, служебный MAX-бот;
- публичный API, а через него CLI и MCP.

**Не входит:** личный и групповой чат сотрудников (следующий подпроект, на ядре из раздела 3), чек-листы, доска Канбан, повторяющиеся задачи, уведомления в Telegram и по email.

**Порядок:** реализация начинается после каналов MAX/ZZAP/DROM и русской локали. Служебный MAX-бот использует HTTP-клиент пакета `integrations/max`.

## 2. Что уже есть и что переиспользуем

| Есть в ChatbotX | Как используем |
|---|---|
| `InboxTeam` / `InboxTeamMember` | ответственный-команда, упоминание команды |
| `WorkspaceMember.notificationTypes` / `notificationChannels` (сейчас не учитываются worker) | настройки уведомлений: добавляем значения для задач и `max`, worker начинает их учитывать |
| PartyKit (`apps/realtime`, party `workspaces`) | событие `notificationCreated` и обновление ленты задачи |
| S3-хранилище | вложения |
| BullMQ, `upsertJobScheduler` | рассылка уведомлений, напоминания и просрочки |
| Права сотрудников (`onlyAssignedContacts` и др.) | видимость данных контакта внутри задачи |

Неиспользуемая таблица `ConversationParticipant` не трогается.

## 3. Модель данных

Все таблицы в `packages/database` (схема, связи — две правки в `relations/index.ts`, инвариант 2), у всех есть `workspaceId` и индексы по нему.

### 3.1 Задачи

**`Task`**
- `id`, `workspaceId`
- `title` (до 255), `description` (markdown, может быть пустым)
- `status`: `todo` | `in_progress` | `done` | `canceled` (по умолчанию `todo`)
- `priority`: `low` | `normal` | `high` | `urgent` (по умолчанию `normal`)
- `dueAt`, `remindAt` (оба могут быть пустыми; `remindAt` ≤ `dueAt`, если оба заданы)
- `assigneeUserId` / `assigneeTeamId` — задано ровно одно из двух (CHECK)
- `createdByUserId` (пусто, если создал сценарий или API), `createdBySource`: `user` | `flow` | `api`, `createdByLabel` (подпись токена API или название сценария, например «Hermes»)
- `threadId` → `InternalThread` (создаётся вместе с задачей)
- `completedAt`, `remindedAt`, `overdueNotifiedAt`
- `createdAt`, `updatedAt`
- индексы: (`workspaceId`, `assigneeUserId`, `status`), (`workspaceId`, `assigneeTeamId`, `status`), (`workspaceId`, `dueAt`) для открытых задач

**`TaskWatcher`** — `taskId`, `userId`, уникальность пары. Автор и ответственный-сотрудник добавляются автоматически.

**`TaskTarget`** — `taskId` и ровно одна ссылка: `contactId` | `conversationId` | `messageId` (CHECK). При удалении контакта, диалога или сообщения удаляется только связь, задача остаётся. При создании из сообщения создаются три связи: контакт, диалог, сообщение.

### 3.2 Ядро внутренней переписки

Общее для лент задач сейчас и для чата сотрудников потом.

**`InternalThread`** — `id`, `workspaceId`, `type`: `task` (в следующем подпроекте добавятся `direct` и `group`), `createdAt`.

**`InternalThreadMember`** — `threadId`, `userId`, `lastReadAt`. Для ленты задачи участники — наблюдатели задачи; синхронизируются сервисом при изменении наблюдателей.

**`InternalMessage`**
- `id`, `threadId`, `workspaceId`
- `kind`: `comment` | `system`
- `authorUserId` (пусто для `system` и для комментариев через API), `authorLabel` (для API)
- `text` (markdown; упоминания в формате `@[Имя](user:<id>)` / `@[Команда](team:<id>)`)
- `mentions` jsonb: `{ userIds: string[]; teamIds: string[] }`, вычисляется сервером из `text`, клиенту не доверяем
- `attachments` jsonb: `[{ key, name, size, mimeType }]` (S3)
- `systemEvent` jsonb для `system`: `{ type: "status" | "due" | "assignee" | "priority" | "created", from, to, byUserId }`
- `editedAt`, `deletedAt` (мягкое удаление: «сообщение удалено»), `createdAt`

### 3.3 Уведомления

**`Notification`** — `id`, `workspaceId`, `userId`, `type`, `entityType` (`task`), `entityId`, `payload` jsonb (заголовок, краткий текст, автор), `readAt`, `createdAt`; индекс (`userId`, `readAt`, `createdAt`).

**`WebPushSubscription`** — `userId`, `endpoint` (уникальный), `p256dh`, `auth`, `userAgent`, `createdAt`, `lastUsedAt`.

**`UserMessengerLink`** — `workspaceId`, `userId`, `provider` (`max`), `externalUserId`, `linkedAt`; уникальность (`workspaceId`, `userId`, `provider`).

**`MessengerLinkCode`** — одноразовый код привязки: `code` (случайный, 128 бит), `userId`, `workspaceId`, `expiresAt` (15 минут), `usedAt`.

Настройки служебного MAX-бота рабочего пространства (токен — зашифрован через `@chatbotx.io/encryption`) хранятся в отдельной таблице `WorkspaceStaffBot` (`workspaceId`, `provider`, `auth`, `enabled`).

## 4. Бизнес-логика

Цепочка `action | API handler → service → repository → DB` (инвариант 9). Сервисы в `packages/business/src/task/`, `internal-thread/`, `notification/`.

### 4.1 Задачи — `taskService`

- `create(input, actor)` — в одной транзакции создаёт `Task`, `InternalThread`, наблюдателей, связи, системное сообщение `created`; ставит событие `task.assigned`.
- `update(id, patch, actor)` — каждое изменённое поле из (`status`, `dueAt`, `assignee*`, `priority`) пишет системное сообщение. Смена ответственного → `task.assigned` новому. `status → done` ставит `completedAt`; возврат из `done` очищает его. Изменение `dueAt` или `remindAt` очищает `overdueNotifiedAt` / `remindedAt`.
- `take(id, actor)` — для задачи на команду: если actor в команде, ответственный становится actor.
- `complete(id, actor)` — сокращение для `status = done`.
- `delete(id, actor)` — только автор или владелец пространства; удаляет задачу, ленту, связи.
- `list(filter, scope)` — вкладки (`mine`, `createdByMe`, `watching`, `myTeams`, `all`), фильтры (статус, приоритет, срок: `overdue` / `today` / `week` / `none`, ответственный, контакт, диалог), пагинация курсором, сортировка по сроку (пустые — в конце), затем по приоритету.
- **Права изменения:** автор, ответственный (или любой участник команды-ответственного), владелец. Комментировать может любой сотрудник пространства.
- **Видимость:** все сотрудники пространства видят все задачи. Данные контакта в задаче возвращаются только если у сотрудника есть доступ к контакту по существующим правам (`onlyAssignedContacts`), иначе связь отдаётся как `{ type: "contact", hidden: true }`.

### 4.2 Лента — `internalThreadService`

- `postComment(threadId, { text, attachments }, actor)` — вычисляет `mentions` (только существующие сотрудники и команды этого пространства), сохраняет, публикует realtime-событие, ставит событие `task.commented` и `task.mentioned`. Упомянутый сотрудник автоматически становится наблюдателем.
- `edit` / `delete` — только автор, в течение 24 часов (после — только удаление владельцем пространства).
- `markRead(threadId, actor)` — обновляет `lastReadAt`.
- **Вложения:** загрузка через существующий механизм presigned URL в S3, до 10 файлов по 25 МБ на сообщение; ключи привязываются к `workspaceId`, выдача — через подписанные ссылки с ограниченным сроком.

### 4.3 Уведомления — `notificationService` и worker

**События и получатели** (автор события никогда не получает уведомление о собственном действии):

| Событие | Получатели |
|---|---|
| `task.assigned` | ответственный; для команды — все её участники |
| `task.mentioned` | упомянутые сотрудники; участники упомянутых команд |
| `task.commented` | наблюдатели, кроме упомянутых в этом же комментарии (они уже получили `task.mentioned`) |
| `task.statusChanged`, `task.dueChanged` | наблюдатели |
| `task.reminder` | ответственный (для команды — участники) |
| `task.overdue` | ответственный (для команды — участники) и автор; один раз |

**Поток:** сервис создаёт записи `Notification` (по одной на получателя) → публикует `notificationCreated` в PartyKit адресно пользователю → ставит задачу в очередь `notificationDispatch` (новая, в `packages/worker-config`) → worker по настройкам сотрудника отправляет push в браузер и сообщение в MAX.

**Настройки:** в `notificationTypes` добавляются `taskAssigned`, `taskMentioned`, `taskCommented`, `taskStatusChanged`, `taskReminder`, `taskOverdue`; в `notificationChannels` — `max`. Значения по умолчанию для новых и существующих сотрудников: все типы задач включены; каналы — центр уведомлений всегда, push в браузере и MAX — после того как сотрудник их подключил. Центр уведомлений отключить нельзя.

**Склейка:** для push и MAX события по одной задаче одному получателю в окне 60 секунд склеиваются в одно сообщение («3 новых события в задаче …»). Реализация: отложенная задача BullMQ с `jobId = dispatch:<userId>:<taskId>` и задержкой 60 с; повторные события дописываются в неё. В центре уведомлений события не склеиваются.

**Напоминания и просрочки:** планировщик `taskDueScan` раз в минуту выбирает задачи со статусом `todo` / `in_progress`, у которых `remindAt ≤ now AND remindedAt IS NULL` или `dueAt ≤ now AND overdueNotifiedAt IS NULL`; флаг ставится условным `UPDATE … WHERE … IS NULL RETURNING`, поэтому при параллельных worker уведомление уходит ровно один раз. Задачи владельцев с блокировкой пропускаются (`withBlockedOwnerGuard`, инвариант 15).

### 4.4 Push в браузере

- VAPID-ключи в env (`WEB_PUSH_VAPID_PUBLIC_KEY`, `WEB_PUSH_VAPID_PRIVATE_KEY`, `WEB_PUSH_SUBJECT`); без них функция скрыта в интерфейсе.
- Service worker `apps/builder/public/sw.js`: показывает уведомление, по клику открывает ссылку на задачу.
- Подписка: в профиле кнопка «Включить уведомления в браузере» → `PushManager.subscribe` → сохранение `WebPushSubscription` (приватный API, как device tokens).
- Отправка из worker библиотекой `web-push`; ответы 404/410 удаляют подписку.
- Ограничения: только HTTPS; на iPhone — только если сайт добавлен на экран «Домой». Это указывается в интерфейсе рядом с кнопкой.

### 4.5 Служебный MAX-бот

- Отдельный бот, не клиентский канал. Токен вводит владелец в «Настройки → Уведомления → MAX-бот»; сохраняется зашифрованным в `WorkspaceStaffBot`.
- Вебхук бота: `POST /integrations/max-staff/webhook?ws=<workspaceId>` с секретом; регистрируется при включении бота. Обрабатывает только `bot_started` / `/start <code>`: находит `MessengerLinkCode`, проверяет срок и неиспользованность, создаёт `UserMessengerLink`, отвечает «MAX подключён к ChatbotX». На любые другие сообщения отвечает подсказкой.
- Сотрудник в профиле нажимает «Подключить MAX» → получает ссылку `https://max.ru/<bot>?start=<code>` и QR-код.
- Сообщение уведомления: заголовок, краткий текст (до 500 символов), кнопка-ссылка «Открыть задачу».
- HTTP-клиент берётся из `integrations/max`; регистрация бота как клиентского канала не происходит.
- Отписка: «Отключить MAX» в профиле удаляет `UserMessengerLink`; если бот получает ошибку «пользователь заблокировал бота», связь удаляется автоматически.

## 5. Интерфейс

Все строки — через `useTranslations()`, ключи сразу в `en.json` и `ru.json`. Мутации инвалидируют кэш TanStack Query (инвариант 21): новый `useInvalidateTasks`, а для уведомлений — `useInvalidateNotifications`.

- **Страница «Задачи»** (`/space/[workspaceId]/tasks`), пункт в боковом меню со счётчиком «мои открытые просроченные». Вкладки: «Мои», «Поставленные мной», «Наблюдаю», «Мои команды», «Все». Фильтры по разделу 4.1. Строка задачи: статус (переключается кликом), название, ответственный, срок (красный, если просрочен), приоритет, связанный контакт, число непрочитанных комментариев.
- **Карточка задачи** — боковая панель (и прямая ссылка `/tasks/<id>`): слева поля, справа лента с комментариями и системными событиями, поле ввода с выпадающим списком упоминаний по `@` (сотрудники и команды) и прикреплением файлов. Кнопка «Взять себе» для задач на команду.
- **Создание задачи** — диалог: название, описание, ответственный, наблюдатели, срок, напоминание (быстрые варианты: «за 15 мин», «за 1 час», «за день»), приоритет, связи.
- **Контакт и диалог:** блок «Задачи» в панели контакта (открытые задачи, кнопка «Создать» с предзаполненной связью). У каждого сообщения клиента пункт меню «Создать задачу»: текст сообщения подставляется в описание (цитатой), связи с контактом, диалогом и сообщением создаются автоматически. В заголовке диалога значок с числом открытых задач.
- **Колокольчик** в верхней панели: счётчик непрочитанного, список последних 50, «Прочитать всё», клик — переход и отметка прочитанным.
- **Профиль → Уведомления:** переключатели типов, «Включить уведомления в браузере», «Подключить MAX» / «Отключить MAX».
- **Настройки → Уведомления → MAX-бот** (только владелец): токен бота, переключатель «Включён», проверка токена.

## 6. Публичный API, CLI, MCP

По инварианту 23: процедуры в `apps/builder/src/features/tasks/api/public.ts`, вложены в `routers/public.ts`, защищены `workspaceTokenAuthAPIForScope("tasks")`. Публичный API делается **до** интерфейса; интерфейс и API вызывают одни и те же методы сервисов.

| Процедура | Назначение |
|---|---|
| `tasks.list` | фильтры из раздела 4.1 (вкладки, кроме личных `mine` / `watching`, заменяются фильтрами `assigneeUserId` / `watcherUserId`) |
| `tasks.get` | задача со связями и наблюдателями |
| `tasks.create` | создание; `createdBySource = api`, `createdByLabel` — имя токена |
| `tasks.update` | изменение полей |
| `tasks.complete` | завершение |
| `tasks.delete` | удаление |
| `tasks.addWatcher` / `tasks.removeWatcher` | наблюдатели |
| `tasks.comments.list` / `tasks.comments.create` | лента: чтение и комментарий от имени токена (`authorLabel`) |

- В `summary` и `description` указано, откуда брать id: `contactId` — `contacts.list`, `conversationId` — `conversations.list`, `messageId` — `conversations.messages`, `userId` — `workspaceMembers.list`, `teamId` — `teams.list`.
- Ответы — машиночитаемые данные (id, статусы, ISO-даты, ссылка `url` на задачу в интерфейсе).
- После изменения API — навык `cli-mcp-docs` (CLI и MCP получают операции из `public-spec.json`, обновляются документация и навыки).
- **Без публичного API (исключения инварианта 23):** центр уведомлений, подписки web push, привязка MAX сотрудника — личные настройки и техническая инфраструктура интерфейса; настройка служебного бота — администрирование уведомлений, доступное владельцу в интерфейсе.

## 7. Шаг сценария «Создать задачу»

- Тип узла `createTask` в `packages/flow-config`; регистрируется во всех реестрах узлов (инвариант 16: `flowVersionSchema`, `allNodesConfig`, `allSteps`, `viewerNodeTypes`, `analyticsNodeTypes`).
- Поля: название и описание с переменными (`{{contact.name}}`, `{{last_message}}` и др.); ответственный — конкретный сотрудник, команда или «назначенный на диалог» (если на диалог никто не назначен — выход «ошибка»); срок — через N минут / часов / дней или пусто; напоминание — за N минут до срока или пусто; приоритет.
- Связи с текущим контактом и диалогом создаются автоматически; `createdBySource = flow`, `createdByLabel` — название сценария.
- Выходы: «успех», «ошибка» (ответственный удалён, команда пуста, не задан назначенный). Строится по навыку `flow-step-development`.
- Id созданной задачи сохраняется в переменную шага, чтобы следующие шаги могли его использовать.

## 8. Ошибки и граничные случаи

| Ситуация | Поведение |
|---|---|
| Ответственный удалён из пространства | задача остаётся, ответственный становится пустым → задача переводится на владельца пространства с системным сообщением |
| Команда-ответственный удалена | то же, на владельца |
| Упомянут несуществующий или чужой сотрудник | упоминание игнорируется, текст остаётся как есть |
| Push: подписка недействительна (404/410) | подписка удаляется |
| MAX: бот заблокирован сотрудником | связь удаляется, сотруднику показывается предупреждение в профиле |
| MAX/push временно недоступны | 3 повтора с увеличивающейся паузой, затем запись в журнал; центр уведомлений не затрагивается |
| Связанный контакт удалён | связь удаляется, в карточке задачи «контакт удалён» (по системному сообщению) |
| Пространство с истёкшим пробным периодом | чтение и удаление задач разрешены, создание и изменение — нет (как для остальных сущностей, инвариант 14) |

## 9. Тестирование

Vitest; внешние сервисы (MAX, web push) подменяются.

- `taskService`: создание (поток, наблюдатели, системное сообщение), переходы статусов и `completedAt`, «взять себе», права изменения, видимость контакта при `onlyAssignedContacts`, перевод на владельца при удалении ответственного.
- Разбор упоминаний: формат, фильтрация чужих id, авто-добавление в наблюдатели.
- `notificationService`: получатели по каждому событию, исключение автора, отсутствие дубля «упомянут + прокомментировал», учёт настроек.
- Склейка уведомлений в окне 60 с.
- `taskDueScan`: ровно одно напоминание и одна просрочка при параллельном запуске; сброс флагов при переносе срока.
- Привязка MAX: код одноразовый и истекает; повторное использование отклоняется.
- Публичный API: создание и чтение, отсутствие доступа к задачам чужого пространства, метки `api` и `createdByLabel`.
- Шаг сценария: успех, ошибка при пустом назначенном, переменные в названии.

## 10. Этапы реализации

1. Таблицы (`Task`, `TaskWatcher`, `TaskTarget`, `InternalThread*`, `InternalMessage`), сервисы, публичный API задач и комментариев.
2. Интерфейс задач: страница, карточка, создание, блоки в контакте и диалоге.
3. Лента: комментарии, упоминания, вложения, realtime-обновление.
4. Уведомления: `Notification`, колокольчик, realtime, настройки, `taskDueScan`.
5. Push в браузере.
6. Служебный MAX-бот (требует этап MAX из спеки каналов).
7. Шаг сценария `createTask` и «Создать задачу» из сообщения клиента.

Каждый этап закрывается зелёными `pnpm lint`, проверкой типов и тестами. Миграции генерируются и показываются пользователю; применяются только после явного разрешения.

## 11. Следующий подпроект (для справки, не входит)

Чат сотрудников: типы `InternalThread` `direct` и `group`, список чатов, непрочитанное по `lastReadAt`, кнопка «Сделать задачей» на сообщении. Упоминания, вложения, realtime и уведомления берутся из этого подпроекта без изменений.
