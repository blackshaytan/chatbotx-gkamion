# Входящие: где нужен менеджер — дизайн

Дата: 2026-10-21
Ветка: `feature/ru-channels-max-zzap-drom`
Статус: черновик, ждёт утверждения пользователем

## 1. Цель

После подключения внешнего ИИ-агента (Hermes) большую часть диалогов ведёт бот. Менеджеру нужно сразу видеть, какие диалоги ждут человека, получать уведомления только по ним и понимать, о чём просит клиент.

Согласовано с пользователем (пункты из обсуждения 21.10):

1. После передачи от агента бот сам не возвращается; в шапке диалога — «Ждёт менеджера».
2. Счётчик непрочитанных сообщений клиента в строке списка: яркий — диалог ждёт менеджера, серый — с клиентом говорит бот.
3. Не уведомлять менеджеров, пока с клиентом говорит агент; уведомлять при передаче и когда диалог ждёт менеджера.
4. Поднимать диалог вверх списка только по сообщениям клиента и менеджера, не бота.
5. Категория при передаче (Срочно, Возврат, Оплата, Статус заказа, Доставка, Цена и срок, Прочее): метка в строке и фильтр.

**Не входит:** уведомления в браузере и звук в веб-версии (сейчас их нет вообще; отдельная задача), учёт личных настроек уведомлений участника (`notificationTypes.*` хранятся, но worker их не читает — отдельная задача), ручная смена категории менеджером (можно позже).

## 2. Что есть сейчас

- Непрочитанность: `lastActivityAt > agentLastReadAt` (`apps/builder/src/features/conversations/lib/is-conversation-unread.ts`, `packages/database/src/queries/conversation-unread.ts`). В строке — синяя рамка вокруг аватара и жирный текст (`conversation-item.tsx`). Счётчика нет.
- Сортировка списка: `lastActivityAt DESC NULLS LAST, id DESC`, индекс `Conversation_workspaceId_lastActivityAt_id_idx` (`list-conversations.query.ts`). В реальном времени `handleNewMessages` поднимает диалог на любое новое сообщение (`chat-store.ts`).
- `lastActivityAt` обновляют и входящие, и сообщения бота (`recordOutboundMessageActivity`, `bumpActivity` по умолчанию `true`), и ответ менеджера (`markAgentReplied`). Поле читают также окно контекста ИИ (`generate-text*/messages.ts`), рейтинги, `last-message-window.ts` и др. — менять его смысл опасно.
- Пауза бота: `conversationService.updateBotEnabled` выбирает `botResumeAt` по политике входящих: для входящих с включённым агентом — `resumeAfterHours` из настроек агента (null — только кнопка). Интерфейс считает бота активным, если `botEnabled` или `botResumeAt` уже прошло (`utils/bot-state.ts`). Поэтому с «через 1 час» после передачи от агента бот возвращается сам.
- Push (Expo): каждое новое входящее → `notifyIncomingMessage` назначенному или всем участникам (`received-message.ts`, `apps/worker/src/notification/handlers/send-push.ts`); состояние бота не учитывается.

## 3. Решение

### 3.1. Передача от агента — без автовозврата

- `externalAgentService.handover` выключает бота с `botResumeAt = null` независимо от `resumeAfterHours`. `resumeAfterHours` остаётся для пауз, когда менеджер сам написал в диалог.
- В `updateBotEnabled`/`disableBotState` добавляется явный параметр «без автовозврата» (а не новая ветка по `triggerContext`), чтобы правило было видно в коде.
- Шапка открытого диалога: если бот выключен и `botResumeAt = null` после передачи от агента (есть категория/время передачи, см. 3.5) — плашка «Ждёт менеджера · <категория>» с кнопкой «Вернуть боту» (существующий `enableBotAction`). Если бот на паузе с `botResumeAt` в будущем — «Бот на паузе до ЧЧ:ММ» с той же кнопкой. Сейчас в этих случаях плашки нет.

### 3.2. Новое поле для сортировки и непрочитанного

Новая колонка `Conversation.inboxActivityAt` (timestamp, nullable):

- обновляется входящим сообщением клиента и сообщением менеджера (`markAgentReplied` и другие пути человека), **не** обновляется сообщениями бота, рассылками и системными заметками;
- миграция: добавить колонку, заполнить `= lastActivityAt` для существующих строк (одним `UPDATE` батчами по `id`, без блокировки таблицы), индекс `(workspaceId, inboxActivityAt DESC NULLS LAST, id DESC)` — `CREATE INDEX CONCURRENTLY` отдельной миграцией;
- `lastActivityAt` не меняется и продолжает обслуживать остальные функции.

Список диалогов сортируется и пагинируется по `inboxActivityAt` (курсор `inboxActivityAt + id`). Непрочитанность везде (строка, фильтр «непрочитанные», поле фильтра контактов `unread`) — `inboxActivityAt > agentLastReadAt`. Ответ менеджера ставит и `inboxActivityAt`, и `agentLastReadAt` — диалог не становится непрочитанным из-за собственного ответа.

В реальном времени `handleNewMessages` поднимает диалог и обновляет `inboxActivityAt` только для входящих сообщений и сообщений менеджера; сообщение бота обновляет только превью.

### 3.3. Счётчик непрочитанных

- В ответ списка диалогов добавляется `unreadCount` — число входящих сообщений клиента (`messageType = incoming`, `type = message`) с `createdAt > agentLastReadAt` (или все, если `agentLastReadAt` null), с потолком 100: подзапрос `LIMIT 100` по индексу `Message_conversation_history_idx`, только для страницы списка (не больше 30–50 строк).
- Строка списка: кружок с числом справа (как в Telegram/WhatsApp), «99+» при 100. Цвет: ярко-красный — диалог ждёт менеджера (бот выключен или на паузе), серый — бот активен. Жирный текст непрочитанного остаётся, синяя рамка вокруг аватара убирается.
- Реальное время: входящее сообщение увеличивает счётчик в store; прочтение (`agentLastReadAt`, событие `conversationUpdated`) обнуляет.

### 3.4. Уведомления

- `enqueueIncomingNotification` не ставится, если входящие диалога обслуживает включённый внешний агент и бот диалога активен (`isConversationActive`). В диалогах без агента поведение не меняется — `botEnabled = true` там не значит, что клиенту кто-то отвечает.
- Новое действие очереди уведомлений `notifyAgentHandover`: при передаче от агента — push назначенному менеджеру или всем участникам: «ИИ-агент передал диалог: <имя клиента> · <категория>», текст — причина (обрезка до 150 символов). Ставится из `externalAgentService.handover` один раз (только когда бот был включён).
- После передачи (бот выключен) входящие клиента уведомляют как сейчас.

### 3.5. Категория передачи

- Фиксированный список ключей: `urgent`, `return`, `payment`, `orderStatus`, `delivery`, `priceAndTerm`, `other`; подписи с эмодзи из примера пользователя через i18n во всех 22 локалях.
- Хранение: колонки `Conversation.handoverCategory` (text, nullable) и `Conversation.handedOverAt` (timestamp, nullable). Ставятся в `handover`, очищаются при возврате боту (`enableBotState`). Нужны в строке списка без лишнего join — поэтому в `Conversation`, а не в `ExternalAgentConversationState`.
- Публичный API `externalAgent.handover`: новый необязательный параметр `category` (enum, по умолчанию `other`). Описание параметра перечисляет значения, чтобы агент выбирал сам. Заметка в диалоге показывает категорию.
- Строка списка: метка категории рядом с именем, пока диалог ждёт менеджера. Фильтр списка: новое поле «Категория» в окне фильтров (множественный выбор).
- `SOUL.md` профиля `assistant`: правило выбора категории.

## 4. Публичный API (агент-first)

- `externalAgent.handover`: + `category`.
- `conversations.list` / `conversations.get`: + `unreadCount`, `inboxActivityAt`, `handoverCategory`, `handedOverAt` в ответе; + фильтр `handoverCategory` в `conversations.list`.
- После изменений — навык `cli-mcp-docs` (README MCP/CLI).

## 5. Тесты

- business: `handover` — `botResumeAt = null`, категория сохраняется, `notifyAgentHandover` ставится один раз; `enableBotState` очищает категорию.
- worker: входящее в диалоге с активным агентом и включённым ботом — без push; после передачи — push есть; диалог без агента — push как раньше; сообщение бота не меняет `inboxActivityAt`.
- builder: `unreadCount` и сортировка по `inboxActivityAt` в запросе списка; store поднимает диалог только по входящему/менеджеру; цвет счётчика; плашки «Ждёт менеджера» / «Бот на паузе до».
- База: проверка, что миграция заполняет `inboxActivityAt`, drift guard.

## 6. Риски

- Сортировка по новой колонке до завершения заполнения даст «пустые» диалоги внизу — поэтому заполнение в той же миграции до переключения кода.
- Подзапрос счётчика на больших диалогах — ограничен `LIMIT 100` и размером страницы.
- Скрытие push для диалогов с агентом: если агент «завис», менеджер узнает о диалоге только через передачу при ошибке — она уже есть (`failToHuman` при сбоях и таймауте).
- Миграция — только с отдельного разрешения пользователя.
