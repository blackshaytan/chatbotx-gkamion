# Чат сотрудников (Staff chat v1) — дизайн

Дата: 2026-10-27
Ветка: `feature/ru-channels-max-zzap-drom`
Статус: решения раздела 12 зафиксированы (D1, D4–D6, D9); реализация по этапам раздела 10

## 1. Цель и контекст

Дать сотрудникам рабочего пространства личную переписку 1:1 внутри ChatbotX: быстро спросить коллегу, переслать файл, превратить сообщение в задачу. Принцип из спеки задач: **чат — для скорости, задачи — для ответственности**; чат строится на том же ядре внутренней переписки (`InternalThread` / `InternalThreadMember` / `InternalMessage`), которое уже несёт ленты задач (раздел 11 спеки `2026-10-17-team-tasks-design.md`). ИИ-агент (Hermes) и другие API-клиенты работают с чатами через публичный API (инвариант 23).

**Входит (v1):**
- личные чаты 1:1 между сотрудниками пространства (get-or-create, одна пара — один чат);
- страница «Чаты» в боковом меню с общим счётчиком непрочитанного; список чатов (собеседник, онлайн-точка, превью, непрочитанные, сортировка по последнему сообщению);
- лента сообщений: редактор TipTap, вложения с подписанными ссылками, правка и удаление, «прочитано», маркер «прочитано собеседником»;
- уведомление в колокольчике (одно непрочитанное на чат) и обновление интерфейса в реальном времени;
- «Создать задачу» из сообщения;
- публичный API со scope `chats` (opt-in, см. D6; полный доступ ко всем чатам пространства для токенов с явным `"chats"`), включая личные сообщения от агента сотруднику;
- только чтение для сессий поддержки платформы.

**Не входит:** групповые чаты (схема их не блокирует, раздел 3.4), упоминания `@` в личных чатах и тип `chatMentioned` (решение D3), реакции, ответы-цитаты, поиск по чатам, push/MAX-доставка (ждут этапов 5–6 задач), шаг сценария «написать сотруднику», чат с самим собой, закрепление и архив, очистка файлов удалённых чатов.

| `workspaceTokenAuthAPIForScope`, реестр scope токенов | новый scope `chats` |

Факты, проверенные в коде и влияющие на дизайн:
- `internalThreadRepository.deleteMembersForUser` (вызывается из `taskService.reassignFromMember` при удалении сотрудника) удаляет участие пользователя **во всех** лентах пространства. Для чатов это потеря членства и непрочитанного; метод ограничивается `type = 'task'` (раздел 8, обязательная правка).
- `markRead` задач — POST, он **не** в `READ_ONLY_POST_PATHS`, поэтому при истёкшем триале закрыт. Для чатов путь добавляется в этот список (раздел 8); для задач — отдельный вопрос вне этой спеки.
- `Notification.type` / `entityType` — `text` (типизация на уровне TS), `payload` — jsonb: расширение типов не требует миграции данных.
- Scope `chats` **не** наследуется токенами с `scopes = NULL`: только явное `"chats"` в массиве (решение D6). Токен Hermes / `{{api_key}}` получает доступ после одобренного data-step (явный список областей + `chats`).
- `workspaceAuthorizedMidddleware` кладёт в контекст `workspaceMember`, но не `isSupportSession`, хотя `resolveWorkspaceAccess` его возвращает — добавляем флаг в контекст (раздел 4.6).

## 3. Модель данных

Одна миграция (`make:migration staff_chat`); показывается пользователю, применяется только после явного «да» (AGENTS.md, «Migration safety»); `db:check-drift` чистый.

### 3.1 `InternalThread` — новые поля и значения

- `type` (enum `internalThreadType`): к `task` добавляются `direct` (чат двух сотрудников) и `agent` (личный канал «API-клиент → один сотрудник», решение D1). `group` добавится позже одним `ALTER TYPE … ADD VALUE`. **Новые значения нельзя использовать в той же миграции** (PostgreSQL: «unsafe use of new enum value» внутри транзакции) — поэтому в индексах миграции нет предикатов по `type`.
- `title` text, пусто — название для `agent`-чата (подпись токена); для `direct` не заполняется (имя — собеседник). Пригодится группам.
- `directKey` text, пусто — ключ дедупликации: для `direct` — `<меньший userId>:<больший userId>` (сравнение как `BigInt`), для `agent` — `agent:<userId>:<подпись токена>`. У лент задач `NULL`.
- `lastMessageAt` timestamp, пусто — время последнего сообщения-комментария; обновляется атомарно с вставкой сообщения (3.5).
- Индексы: `uniqueIndex("InternalThread_workspaceId_directKey_key").on(workspaceId, directKey)` (`NULL` не конфликтуют — задачи не затронуты); `index("InternalThread_workspaceId_type_lastMessageAt_idx").on(workspaceId, type, lastMessageAt desc)`.
- Колонки без `.default()` — вставки пишут значения явно (AGENTS.md: «`.default()` — не гарантия БД»); новые колонки допускают `NULL`, так что существующие вставки задач не ломаются.
- Значения enum — в `internalThreadTypeValues` (`packages/database/src/partials/task.ts`); `Record<InternalThreadType, …>` по коду нет (проверено).

### 3.2 `InternalThreadMember`

Без изменений схемы. `direct`: ровно две строки (создаются в одной транзакции с чатом), `agent`: одна (сотрудник). `lastReadAt` у обоих при создании = момент создания (первые сообщения для собеседника — непрочитанные). Строки **не удаляются** при выходе сотрудника из пространства (раздел 8).

### 3.3 `InternalMessage`

Без изменений схемы. Чат использует только `kind = comment`; `mentions` всегда пишется явно как `{ userIds: [], teamIds: [] }` (в личных чатах упоминания не распознаются, D3), `attachments` — явно. `systemEvent` не используется. Лимит текста — тот же, что у комментария (10 000), константа `CHAT_LIMITS` рядом с `TASK_LIMITS`.

### 3.4 Совместимость с будущими групповыми чатами

Ничего из перечисленного не мешает `group`: `type`, `title`, `InternalThreadMember` (N участников), `lastMessageAt`, общий `countUnreadByThreads`. Для группы `directKey = NULL`. Права «добавить/убрать участника» и системные сообщения (`kind = system`) — отдельная спека.

### 3.5 Уведомления: тип и индекс

Колонки `Notification` не меняются, расширяются только типы TS:
- `type`: `TaskNotificationType | "chatMessage"` (новый `chatNotificationTypes`);
- `entityType`: `"task" | "chat"`, `entityId` для чата = id чата;
- `payload`: объединение по `entityType`. Для чата: `{ actorUserId, actorLabel, excerpt, count, lastMessageId, lastMessageAt }` (`count` — число сообщений с момента создания этой непрочитанной записи). Старые строки задач не трогаются.

В миграцию входит **частичный уникальный индекс** (основа склейки, 4.4):

```sql
CREATE UNIQUE INDEX "Notification_chat_unread_key"
  ON "Notification" ("workspaceId", "userId", "entityId")
  WHERE "entityType" = 'chat' AND "readAt" IS NULL;
```

### 3.6 Прочее

- Реестр scope токенов: значение `chats` в `workspaceApiTokenScopes` (колонка `text[]`, миграции нет) + `workspace-token-scopes.ts` (`order: 16`, ключ `fields.tokenScopes.chats`).
- Настройки: `workspaceMemberNotificationTypesSchema` получает необязательный `chatMessage: boolean` (нет ключа = включено).
- Связи (`relations/*`): `InternalThread` уже связана с участниками и сообщениями; новых таблиц нет, правок `relations/index.ts` не требуется.

## 4. Бизнес-логика

Цепочка `action | API handler → service → repository → DB` (инвариант 9). Новый `packages/business/src/chat/` (`service.ts`, `direct-key.ts`, `view.ts`, `index.ts`) и `packages/database/src/repositories/chat/repository.ts` (список, открытие, `lastMessageAt`). Публичная и приватная процедуры одного действия вызывают **один метод** `chatService`; приложение решает только область видимости (`scope`) и актора. Круги импорта: `chat/**` не импортирует `platform/settings`, `platform/realtime-broadcast`, `workspace/service`, `workspace-member/service`; ссылки (`url`) и realtime — слой builder (как у задач).

### 4.1 Открытие чата — `chatService.open`

- Вход: `{ workspaceId, userIds: [a] | [a, b], actorLabel? }`.
  - Приватный API: `userId` собеседника; пара = (сессия, `userId`); `userId` ≠ сессия (чат с собой — запрещён).
  - Публичный API (токен): `userIds: [a, b]` — чат между двумя сотрудниками; `userIds: [a]` — личный канал агента сотруднику `a` (D1), подпись берётся из имени токена.
- Проверки: все `userIds` — текущие `WorkspaceMember` этого пространства (реальные строки; синтетические участники поддержки — нет), без дублей; иначе `validationException`.
- **Get-or-create без гонок:** в транзакции `INSERT INTO "InternalThread" (…, directKey) … ON CONFLICT (workspaceId, directKey) DO NOTHING RETURNING *`. Если строка вернулась — вставляем участников (в том же `tx`). Если нет — конфликт: параллельная транзакция владеет ключом, `ON CONFLICT` дожидается её завершения, после чего обычный `SELECT` по `(workspaceId, directKey)` видит зафиксированный чат вместе с участниками (READ COMMITTED). Результат — один и тот же чат при любом числе одновременных вызовов.
- Пустой чат (`lastMessageAt IS NULL`) в списках по умолчанию скрыт (в том числе от создателя: интерфейс переходит прямо на `/chats/<id>`); после первого сообщения чат появляется у обоих.

### 4.2 Сообщения

- `send({ workspaceId, threadId, text, attachments, actor })` — в одной транзакции: проверка доступа к чату (участник чата для сессии; любой чат пространства для токена; сессия поддержки — запрещено), проверка, что **все** участники чата — текущие сотрудники пространства (иначе «собеседник удалён из пространства», 8), вложения через общий `resolveThreadAttachments` (префикс чата, 10 × 25 МБ, размер и тип из `headObject`), `internalThreadService.postComment` с отключённым распознаванием упоминаний, обновление `lastMessageAt` одним оператором `UPDATE "InternalThread" SET "lastMessageAt" = GREATEST(coalesce("lastMessageAt", '-infinity'), :createdAt)` (безопасно при параллельных отправках). После транзакции — уведомление (4.4) и realtime (4.5); ошибка уведомления не ломает отправку (`logger.error({ err }, …)`).
- `edit` / `delete` — `canEditComment` / `canDeleteComment` с `isOwner = false`: сотрудник — свои сообщения в течение 24 часов (удаление мягкое, «сообщение удалено»); токен правит только сообщения со своей подписью (`authorUserId = null`, тот же `authorLabel`) и может удалить любое (полномочия пространства). **Отличие от лент задач (D5):** владелец пространства не получает права удалять чужие сообщения — он не участник чата и не видит его.
- `listMessages({ threadId, beforeId?, afterId?, limit })` — курсорная пагинация (по `(createdAt, id)`), без `offset`: лента живая, смещение «плывёт» при новых сообщениях. По умолчанию — последние `limit` (≤ 50), порядок ответа — от новых к старым; `afterId` нужен агентам, читающим ответы сотрудника.
- `markRead({ threadId, userId, upToMessageId? })` — `lastReadAt = GREATEST(lastReadAt, createdAt сообщения upToMessageId | now())`: указатель не откатывается и не «съедает» сообщение, пришедшее между загрузкой ленты и отметкой. Возвращает, изменилось ли что-то (если нет — realtime не публикуется, цикла «событие → перезагрузка → отметка» нет). В той же транзакции — отметка прочитанным уведомления этого чата (4.4). Для не-участника (в т. ч. сессия поддержки) — no-op без ошибки.
- Непрочитанные: `countUnreadByThreads` (как у задач; свои сообщения, удалённые и `system` не считаются; токеновые сообщения непрочитаны для всех). Бейдж в меню — **сумма** по чатам пользователя (`chatService.countUnreadTotal`, один агрегат по `type IN ('direct','agent')`).
- Маркер «прочитано»: в ответе приватного `get`/`list` — `peerLastReadAt` (для `direct`); собственное сообщение помечено прочитанным, если `createdAt ≤ peerLastReadAt`. Публично чужие курсоры чтения **не отдаются** (личное состояние, как `unreadCount` у задач).

### 4.3 Список — `chatService.list`

- Вход: `{ workspaceId, scope: { kind: "member", userId } | { kind: "workspace" }, userId? (фильтр для токена), includeEmpty = false, page, perPage }`.
- `member`: чаты, где пользователь — участник, `lastMessageAt IS NOT NULL`, сортировка `lastMessageAt DESC`. `workspace`: все чаты пространства (токен; сессия поддержки, 4.6).
- Элемент: `id`, `type`, `title`, участники `[{ userId, name, removed }]`, `lastMessageAt`, `lastMessage` (последний не удалённый комментарий через `LATERAL` по индексу `(threadId, createdAt desc)`; превью всегда актуально после правок и удалений, отдельное денормализованное поле не нужно), для сессии — `unreadCount`, `peerLastReadAt`.
- Имя и аватар собеседника: клиент берёт из `useWorkspaceMembers` (как лента задач), API отдаёт `name` и `removed` для случая «сотрудника уже нет в справочнике».

### 4.4 Уведомления — склейка «одно непрочитанное на чат на получателя»

Получатели: все участники чата, кроме автора (`actorUserId`). Для сообщений токена (`actorUserId = null`) — все участники (как для действий API у задач). Выключенный тип (`chatMessage = false`) — запись не создаётся. `chatMentioned` не вводится: в личном чате каждое сообщение и так уведомляет единственного собеседника, а упоминание третьего человека, не состоящего в чате, было бы утечкой (D3).

`notificationService.notifyChatMessage({ workspaceId, threadId, recipients, actor, excerpt, messageId, messageAt })` → **один** `INSERT … ON CONFLICT` на пачку получателей (отсортированных по `userId` — одинаковый порядок блокировок, нет взаимных блокировок):

```sql
INSERT INTO "Notification" (…, "type", "entityType", "entityId", "payload", "readAt")
VALUES (…, 'chatMessage', 'chat', :threadId, :payloadWithCount1, NULL)
ON CONFLICT ("workspaceId", "userId", "entityId")
  WHERE "entityType" = 'chat' AND "readAt" IS NULL
DO UPDATE SET
  "payload"   = jsonb_set(EXCLUDED."payload", '{count}',
                  to_jsonb(coalesce(("Notification"."payload"->>'count')::int, 1) + 1)),
  "createdAt" = EXCLUDED."createdAt",
  "updatedAt" = EXCLUDED."updatedAt"
RETURNING "id", "userId";
```

(в Drizzle — `onConflictDoUpdate({ target, targetWhere, set })`). Свойства:
- **Конкурентные отправки** сериализуются блокировкой строки: `count` растёт точно, дублей нет — частичный уникальный индекс не даёт создать вторую непрочитанную запись.
- `createdAt` обновляется, чтобы запись поднималась в колокольчике (сортировка и индекс — по `createdAt`; чистка `purgeOldNotifications` по возрасту не затрагивает свежие).
- **Прочтение:** `notificationRepository.markReadForEntity({ workspaceId, userId, entityType: "chat", entityId, upTo })` = `UPDATE … SET readAt = now WHERE … AND readAt IS NULL AND (payload->>'lastMessageAt')::timestamp <= :upTo`. Если новое сообщение успело обновить запись раньше (строка заблокирована, UPDATE перечитывает условие — READ COMMITTED), условие не выполнится и запись останется непрочитанной — корректно, сообщение новее прочитанного. После прочтения следующее сообщение создаёт новую запись (`count = 1`) — частичный индекс уже не конфликтует.
- Прочтение записи в колокольчике напрямую (`notifications.markRead`) не двигает `lastReadAt` чата: непрочитанные чата считаются отдельно, счётчик в тексте уведомления — «с момента создания записи».
- После `INSERT … RETURNING` — `emitNotificationsCreated` (существующий слушатель шлёт `notificationCreated` адресно; обновлённые записи тоже).
- Удаление/правка сообщения запись уведомления не меняет (текст в колокольчике может устареть до прочтения чата — допустимо). Уведомления уходящего сотрудника удаляются существующим `notificationRepository.deleteForUser`.

### 4.5 Realtime

- Новый топик `RealtimeTopic.staffChats = "staffChats"` (D9; **не путать** с существующим `chat` — события входящих диалогов клиентов) и событие `chatChanged { threadId }` — только id, данные клиент перечитывает со своими правами; `durability: "ephemeral"` в `packages/partysocket-config/src/schemas.ts` + тест реестра. Одного события достаточно для ленты, списка, бейджа и маркера «прочитано».
- **Адресная доставка:** `sendToWorkspaceMember` обоим участникам чата (а не всему пространству) — иначе остальные сотрудники узнавали бы о факте переписки. Публикует слой builder (`features/chats/lib/chat-realtime.ts`, огонь-и-забыть, ошибки не ломают ответ): после `send`, `edit`, `delete` и `markRead` (только если указатель сдвинулся).
- Клиент: `chats-realtime-sync.tsx` в `workspace-realtime-shell.tsx`, инвалидация `orpc.chatsAPI.key()` с объединением событий за 300 мс (инвариант 21). Деплой `apps/realtime` вместе с builder (реестр топиков).
- Онлайн-точки: событий присутствия нет; приватный запрос `presence` с `refetchInterval` 20 с (TTL присутствия — 20 с) только пока открыта страница чатов. Результат ∩ текущие сотрудники пространства (в Redis присутствуют и сессии поддержки по `userId` — отсекаем). Ошибка Redis → пустой список (`withRedisFallback`).

### 4.6 Права, сессии поддержки, заблокированный владелец

- **Участие:** любой сотрудник с реальной строкой `WorkspaceMember`; отдельного бита прав нет. Собеседников можно выбирать среди всех текущих сотрудников (включая владельца).
- **Сессии поддержки (D4, инвариант 19):** у синтетического членства нет строк в `InternalThreadMember`; оно никогда не становится участником, не попадает в выбор собеседника и в «онлайн». Поддержка **видит раздел «Чаты» как остальные разделы, но только на чтение**: приватный `list` принимает `scope: "workspace"` только при `isSupportSession` (иначе `FORBIDDEN`), `get` и `messages.list` отдают любой чат пространства; все мутации (`open`, `send`, `edit`, `delete`, `upload`) отвечают `FORBIDDEN` с проверкой `isSupportSession` в обработчике (как `toggleSupportAccessAction`); `markRead` — no-op, `lastReadAt` и маркер «прочитано» не затрагиваются, `unreadCount = 0`, realtime ей не шлётся. Для этого `workspaceAuthorizedMidddleware` добавляет в контекст `isSupportSession` из `resolveWorkspaceAccess`. Доступ исчезает с выключением `supportAccessUntil` без дополнительных действий.
- **Токены (D6):** scope `chats` — полный доступ ко **всем** чатам пространства (читать, писать, открывать), в том числе личным перепискам двух сотрудников; токен `read_only` — только чтение (GET). Токен не участник чата и не меняет `lastReadAt`.
- **Проверка scope `chats` и `NULL` (D6, обязательная правка кода):** общая семантика «`scopes === null` = все области» описана в `docs/developer/workspace-api-tokens.md` (строки 34–38) и реализована в `requireTokenScope` (`apps/builder/src/orpc.ts`, строки 181–191): доступ **запрещается** только когда `scopes !== null && scopes !== undefined && !required.some((c) => scopes.includes(c))`, поэтому сегодня `null` проходит **любой** маршрут, в том числе будущий `workspaceTokenAuthAPIForScope("chats")` (строки 208–212). Для области **`chats` это недопустимо:** маршруты `chats.*` разрешены **только** если `Array.isArray(scopes) && scopes.includes("chats")`. Значения `scopes === null`, `undefined` или непустой массив **без** `"chats"` → `403 FORBIDDEN` с тем же сообщением, что и для других scope. Реализация — специальная ветка в `requireTokenScope` (или эквивалент), не меняющая поведение остальных областей: для них `null` по-прежнему «все области». В `docs/developer/workspace-api-tokens.md` добавить подраздел «исключение: scope `chats`» (opt-in, не входит в «All scopes»).
- **Hermes / токен по умолчанию:** строка `WorkspaceApiToken` с `scopes = null` (в т.ч. `isDefault`, `{{api_key}}`) **не** вызывает `chats.*` до миграции данных. При выкатке staff chat — одноразовый data-step **только после явного одобрения пользователя:** для токена Hermes (и при необходимости других агентских токенов с `null`) записать явный массив = все значения `workspaceApiTokenScopes` на момент миграции **плюс** `"chats"` (не оставлять `null`, иначе доступ к чатам не появится). Новые токены получают `chats` только через UI/API создания с отмеченной областью.
- **Истёкший триал (инвариант 14):** GET и DELETE открыты (чтение, список, удаление своих сообщений), POST/PATCH закрыты (`open`, `send`, `edit`, `upload`) — существующая проверка `assertWorkspaceOwnerAccessForMethod` в приватной и токенной цепочках. Приватный `markRead` (POST) добавляется в `READ_ONLY_POST_PATHS` (константа `CHATS_MARK_READ_PATH` в `features/chats/lib/api-paths.ts`) — отметка прочитанного не мутирует данные чата, иначе бейдж зависал бы навсегда; публичного эквивалента нет. Запись заблокирована, бейдж и список работают. Интерфейс скрывает поле ввода и показывает баннер состояния.
- **Заблокированный владелец (инвариант 15):** v1 не добавляет worker-задач — уведомление и realtime создаются синхронно в обработчике (как `notifyTask`), `withBlockedOwnerGuard` не нужен. Если позже появится очередь доставки (push/MAX, этапы 5–6 задач), её обработчик обязан использовать `withBlockedOwnerGuard`.

### 4.7 Вложения

- `attachments.ts` обобщается: `threadAttachmentPrefix(workspaceId, { kind: "tasks" | "chats", id })`; существующие `taskAttachmentPrefix`, `uploadTaskAttachment`, `resolveTaskAttachments` остаются тонкими обёртками. Префикс чата — `private/space/<workspaceId>/chats/<threadId>/`; ключ чужого чата отклоняется (`validationException`), как у задач.
- Выдача: вид токена `chatAttachment` (`refId = "<messageId>:<index>"`, срок 1 час) и маршрут `app/media/chat-attachment/[token]/route.ts` по образцу задач; сервис `chatService.findAttachment` проверяет, что сообщение принадлежит чату типа `direct`/`agent` этого пространства и не удалено. Префикс `/media/chat-attachment` — в `PUBLIC_ROUTES` (`lib/public-routes.ts`) и в тест `proxy-public-routes`. Ссылка выдаётся только читателю, прошедшему проверку доступа к чату, поэтому подписанный URL не раскрывается посторонним; nginx и так отдаёт 404 на `/storage/private/`.

## 5. Интерфейс

Все строки — через `useTranslations()` (ключи сразу во все 22 файла `messages/*.json`, русский и английский переведены), мутации инвалидируют TanStack Query (инвариант 21): новый `useInvalidateChats` (список, сообщения, `unreadTotal`) и `useInvalidateNotifications` при отметке прочитанным. Строки — Tailwind-классы, доступность (`aria-label`, клавиатура).

- **Боковое меню:** пункт «Чаты» (иконка `MessagesSquareIcon`, виден всем, рядом с «Задачи») с бейджем = `chats.unreadTotal` (99+). Запрос `unreadTotal` обновляется realtime-событием.
- **Страница** `/space/[workspaceId]/chats` и `/chats/[threadId]`: слева список (ширина ~320 px), справа лента; на узких экранах одна панель с кнопкой «Назад». Список: аватар/инициалы собеседника, **онлайн-точка** (зелёная при присутствии), имя, время последнего сообщения, превью (вложения без текста — «Вложение»; удалено — «Сообщение удалено»; автор «Вы:»), бейдж непрочитанных, выделение активного. Кнопка «Новый чат» → выбор сотрудника (поиск по имени, онлайн-точки, текущий пользователь исключён) → `chats.open` → переход на `/chats/<id>`. Для `agent`-чата — иконка бота и `title`.
- **Лента:** пузыри (свои справа, чужие слева), группировка подряд идущих сообщений одного автора (5 минут) и разделители дней; подгрузка старых при прокрутке вверх (курсор `beforeId`); автопрокрутка вниз, если пользователь у нижней границы; для сообщений токена — подпись `authorLabel` и значок «API». Свои сообщения: «изменено», маркер **«Прочитано»** (по `peerLastReadAt` собеседника; для `agent`-чата маркера нет). Меню сообщения: «Изменить», «Удалить» (по правилам 4.2, на клиенте — те же условия), «Создать задачу» (раздел 7).
- **Поле ввода:** общий `CommentComposer` с адаптерами `uploadAttachment` / `createMessage`; редактор TipTap **без** `@`-подсказок в чатах (D3); Enter — отправить, Shift+Enter — перенос (в задачах остаётся Ctrl/⌘+Enter), скрепка — до 10 файлов по 25 МБ, превью выбранных файлов.
- **Отметка прочитанного:** когда вкладка видима и есть непрочитанные, `markRead({ upToMessageId: самое новое загруженное })` не чаще раза в 2 секунды; в скрытой вкладке — нет.
- **Выход собеседника:** если собеседника нет в пространстве, лента читается, поле ввода заменено плашкой «Сотрудник удалён из пространства», в списке — «(удалён)» без онлайн-точки.
- **Сессия поддержки:** страница «Чаты» открывается; в списке — все чаты пространства (`scope: workspace`), заголовок «Режим поддержки: только чтение»; поле ввода, «Новый чат», правка, удаление, «Создать задачу» скрыты, отметки прочитанного нет.
- **Истёкший триал:** поле ввода и «Новый чат» скрыты, баннер состояния (существующий), чтение и удаление своих сообщений доступны.
- **Колокольчик:** уведомление `chatMessage` — «Новое сообщение от {имя}» / «N новых сообщений от {имя}» + выдержка (до 200 символов; токены упоминаний заменены именами) + время; клик → отметка прочитанным и переход на `/chats/<id>`. URL строит `buildChatUrl` в слое builder; `notifications/api/private.ts` выбирает построитель по `entityType`.
- **Настройки уведомлений** (диалог профиля): переключатель «Сообщения в чатах» (ключ `chatMessage`); `getPreferences` / `updatePreferences` расширяются, существующие ключи не теряются.
- **Токены (D6):** в реестре `workspace-token-scopes.ts` область `chats` — **opt-in** (не входит в пресет «All scopes» / `allScopes: true` → `scopes: null`). В диалоге создания/редактирования токена — отдельный чекбокс «Чаты» с privacy-note: доступ ко всей личной переписке сотрудников пространства (1:1 и agent-каналы API); снятый чекбокс = `chats` не попадает в массив. Для токена с badge «All scopes» (`scopes: null`) чекбокс «Чаты» выключен и помечен как требующий явного выбора (или отдельного токена с явным списком + `chats`).

## 6. Публичный API, CLI, MCP

По инварианту 23: `apps/builder/src/features/chats/api/public.ts`, вложено в `routers/public.ts` (`chats: chatsPublicRouter`), защита `workspaceTokenAuthAPIForScope("chats")`. Публичный API делается **до** интерфейса; приватный `chatsAPI` (`api/private.ts`, `authorizedAPI` + `workspaceAuthorizedMidddleware`) и публичный вызывают одни методы `chatService`. Ни одна процедура не получает `visibility: "default"` — набор по умолчанию MCP (48 инструментов) не меняется; агенты используют `search_tools` → `call_tool` и CLI.

| Процедура | Метод и путь | Назначение |
|---|---|---|
| `chats.list` | GET `/v1/chats` | все чаты пространства; фильтр `userId` (чаты, где участвует сотрудник), `includeEmpty`, `page`, `perPage` ≤ 50 |
| `chats.get` | GET `/v1/chats/{id}` | чат с участниками и последним сообщением |
| `chats.open` | POST `/v1/chats/open` | `userIds: [a, b]` — чат между двумя сотрудниками; `userIds: [a]` — личный канал токена к сотруднику `a` (D1); get-or-create, идемпотентно |
| `chats.messages.list` | GET `/v1/chats/{id}/messages` | сообщения, новые сверху; курсоры `beforeId` / `afterId`, `limit` ≤ 50 |
| `chats.messages.create` | POST `/v1/chats/{id}/messages` | `text` и/или `attachments`; автор — токен: `authorUserId = null`, `authorLabel` = имя токена |
| `chats.messages.update` | PATCH `/v1/chats/{id}/messages/{messageId}` | только `text`; только свои сообщения токена |
| `chats.messages.delete` | DELETE `/v1/chats/{id}/messages/{messageId}` | мягкое удаление любого сообщения (204) |
| `chats.attachments.upload` | POST `/v1/chats/{id}/attachments` | multipart, один файл ≤ 25 МБ → `{ key, name, size, mimeType }`; затем ключи в `chats.messages.create` |
| `chats.presence` | GET `/v1/chats/presence` | `{ onlineUserIds }` — кто из сотрудников сейчас онлайн |

- В `summary`/`description` указано происхождение id: `userIds` — `workspaceMembers.list`; `id` чата — `chats.list` или `chats.open`; `messageId` — `chats.messages.list`; `attachments` — `chats.attachments.upload`. Формат упоминаний в чатах **не** поддерживается — это сказано в описании.
- Ответы — машиночитаемые данные: чат `{ id, type, title, members[{ userId, name }], lastMessageAt, lastMessage, url }`, сообщение `{ id, chatId, authorUserId, authorLabel, text, attachments[{ index, name, size, mimeType, url }], createdAt, editedAt, deleted }`; `url` — ссылка на чат в интерфейсе, `attachments[].url` — подписанная ссылка на 1 час.
- **Как токен открывает чат и пишет сотруднику.** Токен не имеет пользовательской идентичности, поэтому: между людьми — `chats.open({ userIds: [a, b] })` (и затем `messages.create`; обе стороны видят сообщение «от <имя токена>»); **личное сообщение Hermes сотруднику** — `chats.open({ userIds: [a] })` создаёт `agent`-чат «`<имя токена>` ↔ сотрудник `a`» с единственным участником `a` (D1). Сотрудник отвечает в этом чате в интерфейсе; агент читает ответы опросом `chats.messages.list?afterId=<последний известный>`. Отдельного пользователя-бота нет.
- Не отдаётся публично и не имеет публичных процедур (исключения инварианта 23): `markRead` и `unreadCount` / `peerLastReadAt` (личное состояние сессии, как у задач), `unreadTotal` (бейдж меню), уведомления и настройки (личный центр уведомлений).
- После изменения API — навык `cli-mcp-docs`: `apps/cli/README.md`, `apps/mcp-server/README.md`, снимок `public-spec-operations`, тест «не в наборе по умолчанию»; навык Hermes (`/opt/hermes-data/skills/chatbotx/SKILL.md`) — `chats.open`, `chats.messages.create`, правило «личное сообщение сотруднику = `userIds: [a]`», опрос ответов (после выкатки, как для задач).

## 7. «Создать задачу» из сообщения чата

- Пункт меню сообщения (своё и собеседника; не для удалённых, не в режиме поддержки, не при истёкшем триале) открывает `CreateTaskDialog` (этап 7 задач) с `defaultDescription = toMarkdownQuote(text)` плюс строка автора и даты («— {имя}, {дата}»), обрезка по лимиту описания задачи.
- **Связи (`TaskTarget`) не создаются и не добавляются новый вид (D7):** у задач нет цели «сообщение чата», а добавление `internalMessageId` потребовало бы миграции `TaskTarget` и CHECK; личная переписка не должна быть скрыто привязана к задаче, видимой всем. Ссылка на личный чат в описание **не** вставляется (другие сотрудники не могут его открыть, а факт чата раскрывать не нужно).
- В диалоге, открытом из чата, показывается подсказка «Цитата будет видна всем сотрудникам пространства» (инициатор осознанно делится фрагментом).
- Новых публичных процедур нет: диалог вызывает существующий `tasks.create`; агент делает то же двумя вызовами (`chats.messages.list` → `tasks.create` с цитатой в `description`).

## 8. Ошибки и граничные случаи

| Ситуация | Поведение |
|---|---|
| Сотрудник удалён из пространства | строки `InternalThreadMember` сохраняются: у оставшегося чат читается, отправка закрыта плашкой; история не теряется. `taskService.reassignFromMember` вызывает `deleteMembersForUser` только для лент `type = 'task'` (обязательная правка + регрессионный тест). Уведомления удалённого удаляются существующим кодом. Возврат сотрудника в пространство восстанавливает тот же чат (`directKey` тот же) |
| Учётная запись пользователя удалена (`User` каскадом) | его строки участия удаляются каскадом, сообщения остаются с `authorUserId = NULL`; у собеседника плашка «Сотрудник удалён», автор — «Удалённый пользователь» |
| Чат между теми же двумя сотрудниками создают одновременно | один чат: `ON CONFLICT DO NOTHING` + повторное чтение (4.1) |
| Токен пишет в чат с удалённым сотрудником | отправка отклоняется тем же `validationException` (все участники должны быть текущими сотрудниками); `agent`-чат — единственный участник должен быть сотрудником |
| `chats.open` с не-сотрудником, дублем, пустым списком, тремя и более `userId` | 400 `validationException`; для трёх и более — «групповые чаты не поддерживаются» |
| Попытка чата с самим собой (сессия) | 400 |
| Участник пытается открыть чужой чат | как несуществующий (404), существование не раскрывается |
| Сообщение без текста и без файлов | 400 (как у комментариев) |
| Правка/удаление чужого сообщения, или своего старше 24 ч | 403 (общий forbidden, как у комментариев задач) |
| Вложение: чужой префикс, нет объекта, > 25 МБ, > 10 файлов | 400 (как у задач) |
| Нет Redis | онлайн-точки пусты, остальное работает; без realtime клиент обновляется по фокусу окна |
| Блок отправки на истёкшем триале | 403 «Trial expired» (как у остальных POST), интерфейс скрывает ввод |
| Удалено единственное сообщение / последнее сообщение | превью из `LATERAL` пересчитывается; `lastMessageAt` не откатывается назад (сортировка стабильна) |
| Спам токена | колокольчик не засоряется (одна запись на чат), realtime — по событию на сообщение; ограничений частоты v1 не вводит |
| Повторная отправка токеном при сбое сети | возможен дубль (идемпотентных ключей нет); задокументировано, как для комментариев задач |

## 9. Тестирование

Vitest; Redis, S3 и PartyKit подменяются; тесты — в `__tests__/` пакетов, новые файлы — в `.github/workflows/gkamion-checks.yml`.

- `chatService.open`: создание, повторный вызов даёт тот же чат; **параллельные вызовы (Promise.all ×N) → один чат и две строки участников**; порядок пары не важен; сравнение `directKey` числовое (`9` < `10`); не сотрудник / дубль / чат с собой / три id; `agent`-чат и его уникальность по `(userId, подпись)`.
- `send/edit/delete`: права (автор < 24 ч, > 24 ч, владелец **не** удаляет чужое, токен правит свои, токен удаляет любое), чужой чат — 404, вложения (префикс, `headObject`, лимиты), `mentions` всегда пусты, `lastMessageAt` монотонен при параллельных отправках.
- Непрочитанные и `markRead`: свои и удалённые не считаются, не участник → 0 и no-op, `upToMessageId` не откатывает указатель и не «съедает» более новое сообщение, сумма для бейджа, публикация только при сдвиге указателя.
- Уведомления: первая запись и склейка (`count` растёт, одна непрочитанная запись); **конкурентные `notifyChatMessage` (Promise.all) → одна запись, точный `count`**; прочитанная запись → следующее сообщение создаёт новую; гонка «прочтение vs новое сообщение» оставляет запись непрочитанной; автор исключён, токен — уведомляет обоих; выключенный `chatMessage` не создаёт запись; нет ключа → создаётся; уведомление не ломает отправку при ошибке; `updatePreferences` не теряет ключи; список колокольчика строит URL чата.
- Выход сотрудника: `reassignFromMember` **не** удаляет участие в `direct`-чатах, лента задач работает как раньше; отправка в чат с удалённым — отказ; чтение у оставшегося работает.
- Сессия поддержки: `list(scope: workspace)` разрешён только ей, `get/messages.list` читают, все мутации — `FORBIDDEN`, `markRead` — no-op, не попадает в `members`/`onlineUserIds`, `unreadCount = 0`.
- Триал: GET/DELETE проходят, POST/PATCH (`open`, `send`, `edit`, `upload`) — 403, `markRead` проходит (путь в `READ_ONLY_POST_PATHS`; тест списка путей).
- Публичный API: токен без `"chats"` в массиве — 403; `scopes = null` — **403** на `chats.*` (D6); явный список с `"chats"` — доступ; `read_only` — запись закрыта; unit-тест `requireTokenScope("chats")`: deny для `null`, pass только при `scopes.includes("chats")`; `authorLabel` и `authorUserId = null`; чужое пространство недоступно; снимок спецификации (только новые операции, не в наборе по умолчанию, ровно 48 по умолчанию).
- Приватный API: `scope: workspace` без поддержки → `FORBIDDEN`; публичный и приватный обработчики вызывают одни методы сервиса; realtime публикуется адресно обоим участникам.
- Маршрут `/media/chat-attachment`: плохой токен, чужой вид, удалённое сообщение, чужое пространство → 404; успех — заголовки; `proxy-public-routes`.
- Миграция: `db:check-drift` чист; тест на `information_schema` (колонки и индексы — `test:db`); регистрационный тест реестра событий (`chatChanged`, топик `staffChats`, D9).
- Интерфейс: компоненты общего каталога (`CommentComposer` с адаптерами, задачи не сломаны), i18n-тесты 22 файлов.

## 10. Этапы реализации

Каждый этап закрывается зелёными `pnpm lint`, проверкой типов и тестами и может быть выкачен отдельно. Миграции генерируются и показываются пользователю; применяются только после явного разрешения.

1. **Схема и сервисы.** Миграция (`direct`/`agent`, `title`, `directKey`, `lastMessageAt`, индексы, частичный уникальный индекс уведомлений), типы `Notification`, `chatRepository`, `chatService` (open/list/get/send/edit/delete/markRead/unread), обобщение вложений, правка `deleteMembersForUser` (`type = 'task'`), `CHAT_LIMITS`. Тесты раздела 9 (сервисы, гонки, выход сотрудника).
2. **Публичный API и агенты.** Scope `chats` (enum + реестр + i18n токенов, opt-in UI, исключение `NULL` в `requireTokenScope`), `features/chats/api/public.ts`, маршрут `/media/chat-attachment` и вид токена, `presence`, `isSupportSession` в контексте middleware, снимки спецификации, `cli-mcp-docs`, дополнение `docs/developer/workspace-api-tokens.md`, документ `docs/staff-chat.md`. Data-step (после одобрения): Hermes / default token — явный `scopes[]` со всеми областями + `chats`. Проверка на проде: Hermes открывает `agent`-чат и пишет сотруднику.
3. **Страница чатов.** Вынос общих компонентов ленты, приватный `chatsAPI` (+ `markRead`, `unreadTotal`, `presence`, путь в `READ_ONLY_POST_PATHS`), пункт меню с бейджем, список, лента, редактор, вложения, онлайн-точки, «Новый чат», плашки (выход сотрудника, триал), режим поддержки.
4. **Realtime и уведомления.** Топик `staffChats` (D9) и `chatChanged`, `chats-realtime-sync`, `notifyChatMessage` со склейкой, тип `chatMessage` в колокольчике и настройках, прочтение уведомления при `markRead`. Деплой `builder` + `realtime` вместе.
5. **«Создать задачу» и завершение.** Пункт меню сообщения, подсказка о видимости цитаты, обновление `docs/staff-chat.md`, `docs/tasks.md` (ссылка), `AGENTS.md` (строка в «Docs»), навык Hermes, финальный `invariant-guard`.

## 11. Не входит (для справки)

Групповые чаты (`group`, участники, системные сообщения, права), `chatMentioned` и `@` в группах, реакции и ответы-цитаты, поиск по переписке, push/MAX-доставка сообщений (на очереди `notificationDispatch` задач), шаг сценария «написать сотруднику», чат с самим собой, очистка файлов удалённых чатов и неиспользованных загрузок, ключ идемпотентности для токена.

## 12. Решения для пользователя

**Статус: решено** (2026-10-27). Ниже — зафиксированные ответы; остальной текст спеки приведён в соответствие.

| № | Вопрос | Решение |
|---|---|---|
| D1 | Как Hermes пишет сотруднику лично (пользователя-бота нет) | **Принято:** `chats.open({ userIds: [a] })` → отдельный чат `type = agent` с одним участником (сотрудник `a`); один чат на пару (сотрудник, подпись токена), `title` = имя токена |
| D2 | Пустые чаты | **Принято:** скрыты из списков, пока нет первого сообщения |
| D3 | Упоминания в личных чатах | **Принято:** не поддерживаются, `chatMentioned` не вводится |
| D4 | Сессии поддержки | **Принято:** видят раздел и **все** чаты пространства только на чтение; не участники, не пишут, не отмечают прочитанным |
| D5 | Правка и удаление | **Принято:** автор правит/удаляет своё в течение 24 ч; владелец пространства **не** удаляет чужие сообщения в direct-чатах; токен — правка своих, удаление любого |
| D6 | Scope `chats` и `scopes = NULL` | **Принято (изменено):** `chats` только при явном `"chats"` в массиве; `scopes = null` (All scopes, в т.ч. default `{{api_key}}`) **не** даёт `chats.*`. Проверка: для `workspaceTokenAuthAPIForScope("chats")` маршрут разрешён iff `Array.isArray(scopes) && scopes.includes("chats")` — иначе `403` (см. текущую общую логику `requireTokenScope`, `apps/builder/src/orpc.ts:181-191`, и исключение в §4.6). UI: opt-in чекбокс + privacy-note. Hermes: после одобрения — data-step `null` → полный явный список областей + `chats` |
| D7 | «Создать задачу» | **Принято:** только цитата в описании, без нового вида `TaskTarget`, без ссылки на чат |
| D8 | Уход сотрудника | **Принято:** чат сохраняется и читается оставшимся, отправка закрыта; возврат сотрудника восстанавливает чат |
| D9 | Название топика realtime | **Принято:** `staffChats` (`RealtimeTopic.staffChats = "staffChats"`), не путать с `chat` (входящие диалоги клиентов) |
