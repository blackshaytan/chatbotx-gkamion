# Protected DROM contract

All writes remain disabled in production. This artifact does not replace the running MCP.

- `drom_checkout` owns the sole order POST. No form is handed to raw createOrder. It uses the same persistent host cache and flock for every worker of this MCP. The cache is a durable transaction journal, not disposable cache: never delete/rotate it, never start a second writer with a separate state directory, and restore it with its deployment backup. This deployment supports a single host, not replicas with independent filesystems.
- A reservation is fsynced before POST. After any possible POST, every call is reconciliation only, even after crash/restart or absent/delayed search visibility. Zero results cannot prove non-creation. There is no reset/retry tool. No guessed latest-order adoption. Unexpected/multiple results cannot become success.
- Complete native and extra rows, customer identity, delivery and source fingerprint are frozen in the attempt. Exact GUID/hash readback is required; absent identity metadata fails closed. The backend API schema does not promise these fields; the code never substitutes price_id alone or claims verification when metadata is absent. Production readback compatibility must be checked before enabling writes; no real writes are used to establish it here.
- Native checkout delivery contract matches active n8n `order-delivery-address.js`: `/** Save client delivery / PVZ address into gKamion order comment. */`, `ADDRESS_MARKER='[Адрес доставки / ПВЗ'`, and `hasSavedDeliveryAddress()` accepts that marker. Snapshot: `evidence/n8n-delivery-active.txt`, lines 301, 308, 606-635. The documented createOrder operation allows `order[comment]`, not a structured address mutation. We preserve the exact marked address in that field and verify exact readback, carrier and pickup point. If a structured address is also returned and conflicts, verification fails. Success explicitly reports `delivery_address_record=native_order_comment`, not a structured-address update or shipment. No extra PATCH was authorized or added. No truncation of addresses.
- Every open extra request must be mapped to an offer or explicitly dropped in a complete customer-facing composition. Plan token/rows and later exact acceptance bind all prices/qty/terms; a new contact message invalidates acceptance. Native items cannot silently disappear. Selected extras missing a basket block checkout. Removed extras are excluded by explicit basket IDs; no unrequested basket DELETE is issued.
- Transport has a second write gate. MCP only enables writes when the owner explicitly releases the exact source generation via `DROM_WRITE_RELEASE_SHA256`. The supplied artifact and the running production profile have no such release. Old `drom_checkout_form` is permanently blocked.
